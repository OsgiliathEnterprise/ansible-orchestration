## Why

The role acquires Kerberos tickets through ambient shell `kinit` in six task files (`ipa-certs.yml`, `ipa-kubernetes-ca.yml`, `kube-install-join-node.yml`, `ipa-kube-admin-credential.yml`, `ipa-cert-renewal.yml`, `delete-ipa-cleanup.yml`), relying on the default per-user cache (`~/.k5.<user>`). Three fragilities:

1. **Stale/expired ambient tickets** — `kinit` skips acquisition when a cache already exists. A cache holding a 10-hour ticket that has since expired is silently reused, and the downstream `ipa`/`ipa-getkeytab` call fails with an opaque ticket-expired error.
2. **Cross-flow pollution** — flows share one ambient cache per user (on idm: bootstrap, join, renewal, rotation, and delete all touch `~/.k5.root`; on master: safeguard + CA check). A ticket left behind by one flow — possibly for a different principal — becomes the input of the next.
3. **Append-shadowing in rotation** — the renewal flow appends `kubeclusteradm` to a *persistent* keytab that may already hold a stale entry for the same principal (the `kube-cert-renewal` spec forbids appending); today the shell `rm -f` + `ipa-getkeytab` dance is the only thing preventing it.

Additionally, the `ipa-pki-infra` spec's ticket requirement ("a Kerberos ticket is obtained via keytab before cert operations") is loose about cache handling — the code uses the shared ambient cache, and nothing pins down stale-ticket or cross-flow behavior.

## What Changes

- **Scratch ticket caches** — every `kinit` becomes a `community.general.krb_ticket` task that acquires into a dedicated `cache_name` under `/tmp`, preceded by a pre-clear (`file: state=absent`) so a stale/expired ticket can never be reused. Downstream shell consumers inherit the cache via `env: KRB5CCNAME` (including on delegated tasks). Consumer commands themselves are unchanged.
- **Native keytab usability probes** — the two keytab probes (admin-credential keytab-first, renewal rotation) become `krb_ticket: keytab: true` block/rescue probes into scratch caches. Usable keytab mints a fresh ticket; a rotated keytab fails; neither probe reads or writes the ambient cache.
- **Native keytab export, ticket-mode, non-rotating** — the rotation flow's `kinit admin` + `ipa-getkeytab` + `rm -f` shell sequence becomes a single `community.general.ipa_getkeytab` task (`sasl_mech: GSSAPI` against the scratch admin ticket via `env: KRB5CCNAME`, `force: true`, `retrieve_mode: true` / `--retrieve`). The bind-DN alternative was probed and rejected: the true admin DN (`uid=admin,cn=users,cn=accounts,dc=osgiliath,dc=test`, with a version-dependent `cn=users` nesting) is not derivable from `company_domain`, and bind attempts with the derived DN fail with LDAP error 49. `--retrieve` (verified on a running VM) makes the export non-rotating — it fetches the current KDB key without rotating, so the managed password is not invalidated and the keytab tracks the KDB across re-exports. Appending is impossible and change reporting becomes truthful (changed when replaced, no change when the rotation block is skipped in steady state).
- **Passwordless CA #2 client-certificate enrollments (amended in, 2026-11-04)** — the two remaining module-password sites for *client* certs (`kube-node-cert.yml`, `admin-user.yml`) enroll through `freeipa.ansible_freeipa.ipacert` delegated to the IPA master, which negotiates Kerberos natively from a scratch ticket (`environment: KRB5CCNAME`; `ipaadmin_password` is not required by the argspec). Identity follows ordering: node-cert enrollment uses an admin scratch ticket (the `kubeclusteradm` user/keytab do not exist yet at that point, and only admin-class identities may enroll `host/...` principals); admin-cert enrollment is keytab-first for `kubeclusteradm` with an admin-password rescue. The half-migrated draft had used `community.general.ipa_getcert` — a module absent from `community.general` 14.0.0 — which is what broke the switch.
- **Spec** — new `kerberos-ticketing` capability: fresh scratch acquisition, keytab usability probes, native forced ticket-mode export with key-stability (`--retrieve`) contract, and scratch-ticket authentication for the CA #2 client-certificate enrollments; plus a MODIFIED requirement on `ipa-kube-admin-credential` (the export is non-rotating — the "managed password dead by design" clause is superseded).

## Capabilities

### New Capabilities
- `kerberos-ticketing`: scratch-cache ticket acquisition, keytab usability probes, native forced keytab export (ticket mode, non-rotating), scratch-ticket authentication for CA #2 client-certificate enrollments

### Modified Capabilities
- `ipa-kube-admin-credential`: the steady-state keytab export becomes non-rotating (`ipa-getkeytab --retrieve`) — re-export fetches the current KDB key without rotating, so the managed password is no longer invalidated by re-export (the keytab remains the steady-state credential and tracks the KDB; the "dead by design" clause is superseded). `ipa-pki-infra`'s ticket requirement stays as-is; the new `kerberos-ticketing` capability pins down the cache model it leaves open.

## Impact

- **Affected code**: `tasks/ipa-certs.yml`, `tasks/ipa-kubernetes-ca.yml`, `tasks/kube-install-join-node.yml`, `tasks/ipa-kube-admin-credential.yml`, `tasks/ipa-cert-renewal.yml`, `tasks/delete-ipa-cleanup.yml`, plus `env` on the idm-delegated `ipa` CLI consumers in the CA chain (`tasks/ipa-ca-ensure.yml`, `tasks/ipa-ca-profile.yml`, `tasks/ipa-ca-link-profile.yml`), plus the CA #2 client-cert enrollments (`tasks/kube-node-cert.yml`, `tasks/admin-user.yml`)
- **Dependencies**: `community.general` only (already pinned in `requirements-collections.yml`; both `krb_ticket` and `ipa_getkeytab` are present in the installed collection). No new dependencies.
- **Behavioral equivalence**: consumer commands unchanged; only the ticket source moves from ambient to scratch. Ticket tasks report no change (matching today's `changed_when: false` semantics — a ticket cache is ephemeral state, like the existing credential-cache renewal). One deliberate behavior change: the keytab export is non-rotating (`--retrieve`) — re-export no longer invalidates the `kubeclusteradm` managed password (see the `ipa-kube-admin-credential` modified requirement).
- **Docs**: monorepo AGENTS.md `kinit` exception note — the entry stays (other roles — `tcharl.freeipa_server`, `tcharl.ansible_securehost`, `tcharl.nfs_server` — still use shell `kinit`), but this role stops contributing usage sites.
